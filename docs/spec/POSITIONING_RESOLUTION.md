## 一、矛盾根因分析（5-Why）

### 1.1 5-Why 分析

```
现象: PRD_V4 写"全栈 4 P0"，SKILL_FREEZE_LIST 写"聚焦 3 核心"

Why 1: 为什么两个文档不一致？
→ 因为 v4.0 PRD 更新时没有同步 SKILL_FREEZE_LIST

Why 2: 为什么 v4.0 PRD 更新时没同步？
→ 因为 v4.0 PRD 是"愿景扩展"，v0.3.0 冻结是"质量收缩"，两者决策时机不同

Why 3: 为什么会同时存在"扩展"和"收缩"两个方向？
→ 因为 v0.3.0 为了质量达标收缩到 3 核心，但产品愿景仍是全栈

Why 4: 为什么收缩后没有逐步扩展回全栈？
→ 因为收缩后的质量巩固阶段没有明确的"解冻触发条件"

Why 5: 为什么没有解冻触发条件？
→ 因为 v0.3.0 冻结时只定义了"复活条件"（≥2 用户反馈需要），但没有定义
   "何时评估解冻"和"如何评估解冻"的流程
```

### 1.2 根因总结

**根本原因**: v0.3.0 冻结决策是正确的（质量优先），但冻结后**缺少明确的解冻路径和评估机制**，导致 PRD_V4 的"全栈"愿景与实际"3 核心"状态脱节。

**次要原因**:
- v4.0 PRD 更新流程缺少"与现状对齐"环节
- SKILL_FREEZE_LIST 没有"解冻评估时间表"
- 缺少"用户反馈驱动的解冻机制"

## 二、7-Role 共识评估

| 评估项 | 决策 |
|--------|------|
| 矛盾性质 | 不是"谁对谁错"，而是"愿景 vs 现状"的正常差距 |
| 解决方向 | 不否定 v0.3.0 收缩（质量优先正确），也不否定 v4.0 全栈（愿景正确） |

> **7-Role 共识 7/7 通过**

## 三、解决方案

### 3.1 总体策略

**"愿景保留 + 路径明确 + 反馈驱动"**

```
v0.3.0 (2026-06-19)         v0.4.0 (2026-07-18)         v0.5.0 (本方案)
──────────────              ──────────────              ──────────────
冻结 11 技能                质量巩固                     解冻路径明确
聚焦 3 核心                 88.3 分 B+                   种子用户驱动解冻
task/crm 半冻结             矛盾未解决                   PRD_V4.1 同步更新
```

### 3.2 三层解决方案

#### Layer 1: 矛盾调和（立即执行）

**调和原则**: v4.0 全栈是**产品愿景**，v0.3.0 收缩是**当前状态**，两者不矛盾。

**调和表述**:
- PRD_V4.1 §1.2 更新为："一人公司全栈运营系统（愿景） — v0.5.0 当前阶段聚焦 3 核心技能成熟 + task_manager/crm 基于用户反馈解冻"
- SKILL_FREEZE_LIST 更新为："v0.3.0 冻结决策正确（质量优先）；v0.5.0 基于 6 大类型种子用户反馈决定解冻路径"

#### Layer 2: 解冻路径（v0.5.0 执行）

**解冻决策框架**:

```
种子用户反馈
    │
    ├─ ≥2 名用户反馈需要 task_manager → 解冻 task_manager
    │   ├─ 补齐测试覆盖率 ≥80%
    │   ├─ 移除 frozen="semi" 标记
    │   ├─ 解锁所有方法
    │   └─ 更新文档（PRD/SKILL_FREEZE_LIST/README/API）
    │
    ├─ ≥2 名用户反馈需要 crm → 解冻 crm
    │   ├─ 补齐测试覆盖率 ≥80%
    │   ├─ 移除 frozen="semi" 标记
    │   ├─ 解锁所有方法
    │   └─ 更新文档
    │
    ├─ ≥2 名用户反馈需要其他冻结技能 → 评估解冻
    │   ├─ competitor_skill（竞品分析）
    │   ├─ dashboard_skill（仪表盘）
    │   ├─ invoice_skill（发票）
    │   ├─ knowledge_skill（知识库）
    │   ├─ pricing_skill（定价）
    │   └─ social_skill（社交媒体）
    │
    └─ 无用户反馈需要 → 维持冻结，v0.6.0 重新评估
```

#### Layer 3: 长期机制（v0.5.0+ 持续）

**解冻评估周期**:
- 每个版本发布后评估一次（v0.5.0 → v0.6.0 → v0.7.0 ...）
- 评估依据：种子用户反馈 + 商业指标 + PMF 信号
- 评估输出：SKILL_FREEZE_LIST 更新 + PRD 同步

**PRD 与现状同步机制**:
- 每次版本发布前，PM 必须检查 PRD 与现状的一致性
- PRD 中明确标注"愿景"vs"当前阶段"
- SKILL_FREEZE_LIST 作为 PRD 的配套文档，同步更新

### 3.3 解冻决策矩阵

| 反馈强度 | task_manager | crm | 其他冻结技能 |
|---------|-------------|-----|------------|
| ≥3 名用户明确反馈需要 | ✅ 立即解冻 | ✅ 立即解冻 | ✅ 评估解冻 |
| 2 名用户明确反馈需要 | ✅ 解冻 | ✅ 解冻 | ⚠️ 评估解冻 |
| 1 名用户反馈需要 | ⚠️ 评估解冻 | ⚠️ 评估解冻 | ❌ 维持冻结 |
| 0 用户反馈需要 | ❌ 维持半冻结 | ❌ 维持半冻结 | ❌ 维持冻结 |
| 用户反馈不需要 | ❌ 维持半冻结 | ❌ 维持半冻结 | ❌ 维持冻结（考虑移除） |

### 3.4 解冻执行流程

```
种子用户反馈收集（W9-W10）
    │
    ▼
PM 整理反馈（W11）
    │
    ▼
7-Role 共识评估（W11）
    │
    ├─ 决策：解冻 / 不解冻 / 评估
    │
    ▼
[如决策解冻]
    │
    ├─ 1. Coder 移除 frozen 标记
    ├─ 2. Tester 补齐测试覆盖率 ≥80%
    ├─ 3. Coder 解锁所有方法
    ├─ 4. UI 技能市场重新显示
    ├─ 5. PM 更新 PRD_V4.1
    ├─ 6. PM 更新 SKILL_FREEZE_LIST
    ├─ 7. DevOps 更新 README/API
    └─ 8. Tester E2E 验证
    │
    ▼
v0.5.0 发布包含解冻决策
```

## 四、v0.5.0 具体决策

### 4.1 task_manager 解冻条件

**当前状态**: 半冻结（仅 list_tasks 方法维护）

**解冻条件**（满足任一）:
- ✅ ≥2 名种子用户反馈需要任务管理
- ✅ 项目交付者类型用户（≥1 名）反馈需要
- ✅ 飞轮路径验证：用户从单一技能用到"task_manager + report"组合

**解冻后状态**:
- 移除 frozen="semi" 标记
- 所有方法解锁（create_task/update_task/delete_task/list_tasks/...）
- 测试覆盖率 ≥80%
- 技能市场重新显示
- Onboarding 更新（4 核心技能）

**解冻工作量估算**:
- 移除标记 + 解锁方法: 0.5 天
- 补齐测试: 2-3 天
- 文档同步: 0.5 天
- E2E 验证: 0.5 天
- **总计**: 3-4 天

### 4.2 crm 解冻条件

**当前状态**: 半冻结（仅 get_customer/get_customer_stats/get_silent_customers 3 方法维护）

**解冻条件**（满足任一）:
- ✅ ≥2 名种子用户反馈需要客户管理
- ✅ 顾问/教练类型用户（≥1 名）反馈需要
- ✅ 电商运营类型用户（≥1 名）反馈需要
- ✅ 飞轮路径验证：用户从单一技能用到"crm + email"或"crm + report"组合

**解冻后状态**:
- 移除 frozen="semi" 标记
- 所有方法解锁（add_customer/update_customer/get_customer/...）
- 测试覆盖率 ≥80%
- 技能市场重新显示
- Onboarding 更新

**解冻工作量估算**:
- 移除标记 + 解锁方法: 0.5 天
- 补齐测试: 2-3 天
- 文档同步: 0.5 天
- E2E 验证: 0.5 天
- **总计**: 3-4 天

### 4.3 其他冻结技能解冻条件

**当前状态**: 6 个技能完全冻结（competitor/dashboard/invoice/knowledge/pricing/social）

**解冻条件**:
- ≥2 名种子用户反馈需要某技能
- 7-Role 共识评估通过
- 解冻工作量可接受

**解冻优先级**（基于 USER_STORIES 6 大类型）:
| 优先级 | 技能 | 关联用户类型 | 关联场景 |
|--------|------|------------|---------|
| P1 | knowledge | 知识工作者 | 知识整理 |
| P2 | dashboard | 电商运营/顾问 | 数据可视化 |
| P3 | invoice | 电商运营 | 开票 |
| P3 | competitor | 顾问 | 竞品分析 |
| P4 | pricing | 电商运营 | 定价策略 |
| P4 | social | 内容创作者 | 社媒管理 |

**注**: v0.5.0 不主动解冻这些技能，仅记录用户反馈，v0.6.0+ 评估。

### 4.4 report 技能定位澄清

**矛盾**: PRD_V4 未将 report 列为 P0，但 v0.3.0 视为 3 核心之一。

**澄清**: report 技能一直是核心，PRD_V4 §1.3 的"4 P0"是漏写，应在 PRD_V4.1 中明确为**5 P0 技能**：
- email（邮件）
- finance（记账）
- report（报告）
- task_manager（任务管理，v0.5.0 解冻中）
- crm（客户管理，v0.5.0 解冻中）

**理由**: report 是 v0.3.0 收缩后的 3 核心之一，且是飞轮路径的关键节点（report 依赖 finance + crm + task），不应该是非 P0。
