# OPC-Agents v0.1.5 架构师评审报告

## 一、问题逐项评审

### P0 级别

**1. Ollama后端未完整测试**
- **评审意见**: ✅ 同意，这是架构完整性问题
- **架构视角**: 多后端支持是承诺的能力，未验证即发布违反架构契约
- **解决方案**: 
  - 建立LLM Provider集成测试框架
  - 每个后端必须通过标准测试套件（连接、流式、错误处理、超时）
  - 添加后端健康检查接口
- **验收标准**: Ollama后端通过≥20个集成测试用例，覆盖正常/异常/边界场景

**2. 无API Key时模板模式过于简单**
- **评审意见**: ✅ 同意，但优先级建议降为P1
- **架构视角**: 这是降级策略设计问题，不影响核心功能可用性
- **解决方案**:
  - 设计三级降级策略：完整LLM > 本地规则引擎 > 静态模板
  - 引入轻量级规则引擎（基于行业知识库+模板变量替换）
  - 提供"示例模式"展示完整能力
- **验收标准**: 无API Key时生成文档包含≥5个动态章节，内容丰富度达到LLM模式的60%

**3. 异步任务失败恢复机制未测试**
- **评审意见**: ✅ 同意，**VETO项**
- **架构视角**: 这是系统可靠性的基石，生产环境必备
- **解决方案**:
  - 实现任务状态机（pending/running/failed/completed/retrying）
  - 引入消息队列（Celery+Redis或RabbitMQ）实现at-least-once语义
  - 设计幂等性保证机制
  - 实现断点续传和部分结果保存
- **验收标准**: 
  - 模拟5种故障场景（进程崩溃、网络超时、LLM限流、磁盘满、OOM）全部自动恢复
  - 恢复时间<30秒，无数据丢失

### P1 级别

**4. LLM Provider无统一接口**
- **评审意见**: ✅ 强烈同意，**VETO项**
- **架构视角**: 这是架构腐化的根源，技术债会指数级增长
- **解决方案**:
  - 定义`ILLMProvider`抽象接口（参考Langchain设计）
  ```python
  class ILLMProvider(ABC):
      @abstractmethod
      async def generate(self, prompt: str, **kwargs) -> AsyncIterator[str]
      @abstractmethod
      async def health_check(self) -> HealthStatus
      @abstractmethod
      def get_capabilities(self) -> ProviderCapabilities
  ```
  - 实现Adapter模式统一4种后端
  - 引入Provider注册中心和工厂模式
- **验收标准**: 
  - 新增Provider只需实现接口，无需修改业务代码
  - 现有4个Provider迁移完成，代码重复率<10%

**5. 无Docker部署支持**
- **评审意见**: ✅ 同意
- **架构视角**: 容器化是现代应用标配，影响可移植性
- **解决方案**:
  - 提供多阶段构建Dockerfile（开发/生产）
  - docker-compose编排（app+redis+postgres可选）
  - 健康检查和优雅关闭
  - 环境变量配置注入
- **验收标准**: 
  - `docker-compose up`一键启动
  - 镜像大小<500MB
  - 启动时间<30秒

**6. 无用户认证/多用户隔离**
- **评审意见**: ⚠ 部分同意，需明确场景
- **架构视角**: 取决于产品定位（单租户工具 vs SaaS平台）
- **解决方案**:
  - 阶段1（v0.1.5）：基础认证（JWT + API Key）
  - 阶段2（v0.1.5）：多租户隔离（tenant_id + RBAC）
  - 数据隔离：行级安全策略（PostgreSQL RLS）
- **验收标准**: 
  - v0.1.5：支持用户注册/登录，API需token认证
  - 不同用户数据完全隔离，通过渗透测试

**7. API Key明文存储**
- **评审意见**: ✅ 同意，**VETO项**（安全红线）
- **架构视角**: 这是安全架构的基本要求
- **解决方案**:
  - 采用加密存储方案：
    - 方案A：应用层加密（AES-256-GCM + 密钥派生）
    - 方案B：集成密钥管理服务（HashiCorp Vault / AWS Secrets Manager）
  - 传输层TLS强制
  - 审计日志记录访问
- **验收标准**: 
  - 数据库中API Key全部加密存储
  - 通过OWASP Top 10安全扫描
  - 密钥轮换机制可用

**8. 无结构化日志和监控**
- **评审意见**: ✅ 同意
- **架构视角**: 可观测性是生产系统三大支柱之一
- **解决方案**:
  - 日志：结构化JSON日志（structlog）+ ELK/Loki
  - 指标：Prometheus + Grafana（请求量、延迟、错误率、LLM token消耗）
  - 追踪：OpenTelemetry分布式追踪
  - 告警：关键指标阈值告警
- **验收标准**: 
  - 所有日志JSON格式，包含trace_id/user_id/request_id
  - 核心指标dashboard可用
  - 故障场景5分钟内定位根因

### P2 级别

**9. 后端无Mock层**
- **评审意见**: ✅ 同意
- **架构视角**: 测试架构的基础设施
- **解决方案**:
  - 实现MockLLMProvider（可配置响应、延迟、错误）
  - 使用依赖注入框架（如dependency-injector）
  - 录制/回放模式（VCR.py）
- **验收标准**: 
  - 单元测试无需真实API Key
  - CI/CD pipeline运行时间<5分钟

**10. 并发压力未验证**
- **评审意见**: ✅ 同意
- **架构视角**: 性能架构验证必不可少
- **解决方案**:
  - 使用Locust/K6进行压力测试
  - 识别瓶颈（数据库连接池、LLM并发限制、内存）
  - 设计限流策略（令牌桶算法）
  - 异步化改造（FastAPI全异步）
- **验收标准**: 
  - 支持100并发用户，P95延迟<5秒
  - 无内存泄漏，24小时稳定性测试通过

**11. 文档生成质量无量化评估**
- **评审意见**: ⚠ 修改建议：这是产品/算法问题，非架构核心
- **架构视角**: 架构需提供质量评估的扩展点
- **解决方案**:
  - 设计质量评估插件架构
  - 提供基础指标（完整性、一致性、格式规范）
  - 预留AI评估接口（LLM-as-Judge）
- **验收标准**: 
  - 质量评分API可用
  - 支持自定义评估规则

**12. 前端无国际化**
- **评审意见**: ✅ 同意，但优先级最低
- **架构视角**: 架构需支持i18n，但内容翻译可延后
- **解决方案**:
  - 集成i18n框架（react-i18next）
  - 提取所有硬编码文本
  - 先支持中英文
- **验收标准**: 
  - 语言切换功能可用
  - 至少80%界面文本已国际化

**4. LLM Provider无统一接口**
- **评审意见**: ✅ 强烈同意，这是架构债务
- **解决方案**:
  ```python
  # 抽象基类
  class LLMProvider(ABC):
      @abstractmethod
      async def generate(self, prompt: str, **kwargs) -> str: pass
      
      @abstractmethod
      async def stream_generate(self, prompt: str, **kwargs) -> AsyncIterator[str]: pass
      
      @abstractmethod
      async def health_check(self) -> bool: pass
  
  # 工厂模式
  class LLMProviderFactory:
      @staticmethod
      def create(provider_type: str, config: dict) -> LLMProvider:
          ...
  ```
  - 统一错误处理和重试逻辑
  - 统一参数映射（temperature, max_tokens等）
- **验收标准**:
  - 新增Provider只需继承基类，无需修改业务代码
  - 4种后端通过统一测试套件
- **VETO项**: ❌ 非veto，但强烈建议v0.1.5完成
