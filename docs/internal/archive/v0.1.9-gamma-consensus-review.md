## 一、方案概述

### 核心问题

v0.1.7-v0.1.9构建的三贤者架构（策略脑+执行脑+反思脑+共识引擎）代码完整、测试覆盖，但在运行时完全未被调用。用户实际请求走的是旧的TaskEngineV3线性流程。

### 核心思路

**三贤者作为编排层，TaskEngineV3作为执行层**：

```
用户输入 → AgentLoop（编排层）→ TaskEngineV3（执行层）→ 交付结果
             │                      │
             ├── 策略脑：意图理解+规划    ├── 搜索+后处理
             ├── 执行脑：按步骤调度       ├── LLM增强内容生成
             ├── 反思脑：质量评估+修正    ├── 模板降级
             └── 共识引擎：质量把关       └── 多轮对话上下文
```

### 任务分解

| 任务 | 优先级 | 描述 |
|------|--------|------|
| TASK-G1 | P0 | AgentLoop接入主流程 |
| TASK-G2 | P0 | 策略脑替代IntentClassifier |
| TASK-G3 | P0 | 反思脑质量把关 |
| TASK-G4 | P1 | 共识引擎集成 |
| TASK-G5 | P1 | 执行进度可视化接入前端 |
| TASK-G6 | PHASE4-P1 | 技能市场API |
| TASK-G7 | PHASE4-P1 | MCP协议支持 |
| TASK-G8 | PHASE4-P2 | 插件系统 |
| TASK-G9 | PHASE4-P2 | 自定义技能编辑器 |

## 二、七角色审核意见

### 🏗 架构师审核

**结论**: ✅ 有条件通过

**认可点**:
1. 编排层+执行层的分层思路正确，符合单一职责原则
2. 保留TaskEngineV3降级路径是必要的，避免单点故障
3. 复合意图拆解是三贤者架构的核心价值，比IntentClassifier的正则匹配有质的提升

**风险与改进**:

| # | 风险 | 严重度 | 改进建议 |
|---|------|--------|---------|
| A-1 | AgentLoop是async，TaskEngineV3.execute()是sync，异步/同步桥接容易出错 | 🔴高 | 在ExecutorBrain中用`asyncio.get_event_loop().run_in_executor()`包装sync调用，不要直接在async函数中调用sync阻塞方法 |
| A-2 | ExecutorBrain.execute_step()的skill_id到TaskEngineV3方法的映射缺少明确定义 | 🔴高 | 新增`TaskEngineAdapter`类，封装skill_id→TaskEngineV3方法的映射表，而不是在ExecutorBrain中硬编码 |
| A-3 | 反思脑修正循环可能导致无限重试 | 🟡中 | 已有MAX_REFLECT_ROUNDS=3和MAX_CORRECTION_ATTEMPTS=2，但需在AgentLoop层面加总超时限制（如60秒） |
| A-4 | PHASE4的技能市场API和MCP协议与当前架构耦合度需评估 | 🟡中 | 建议先完成G1-G5再启动G6-G9，避免架构变更叠加 |

**架构决策建议**:
- 新增`TaskEngineAdapter`作为ExecutorBrain和TaskEngineV3之间的适配器
- AgentLoop成为前端唯一入口，TaskEngineV3不再被前端直接调用
- 但保留`USE_AGENT_LOOP=false`环境变量开关，紧急时可回退

### 📋 产品经理审核

**结论**: ✅ 通过

**认可点**:
1. "架构断裂"是P0级问题，README宣传的特性用户实际无法使用，必须修复
2. 复合意图拆解（"分析竞品并写方案"→搜索→分析→创作）是用户强需求
3. 质量把关+自动修正是差异化竞争力

**风险与改进**:

| # | 风险 | 严重度 | 改进建议 |
|---|------|--------|---------|
| P-1 | 三贤者引入后响应时间可能增加（反思循环+修正） | 🟡中 | 需定义SLA：单次请求<30秒，修正循环<60秒；超时则降级到TaskEngineV3直接返回 |
| P-2 | 用户不可见三贤者的决策过程，可能困惑"为什么重试" | 🟡中 | 前端显示"正在评估结果质量..."→"质量评分0.45，自动补充搜索..."等进度提示 |
| P-3 | PHASE4功能（技能市场/MCP/插件）范围过大，需拆分版本 | 🟡中 | G6-G7归入v0.2.0，G8-G9归入v0.2.1，避免gamma版膨胀 |

**用户故事补充**:
- US-GAMMA-1: 作为用户，当我输入复合指令时，系统自动拆解并逐步执行，我能看到每步进度
- US-GAMMA-2: 作为用户，当生成结果质量不佳时，系统自动修正而非直接交付半成品
- US-GAMMA-3: 作为用户，我能通过开关选择"快速模式"（跳过反思）或"质量模式"（完整三贤者闭环）

### 🔒 安全专家审核

**结论**: ✅ 有条件通过

**认可点**:
1. 保留降级路径是安全最佳实践
2. TaskEngineV3已有的输入验证和安全防护不需要重复实现

**风险与改进**:

| # | 风险 | 严重度 | 改进建议 |
|---|------|--------|---------|
| S-1 | AgentLoop的反思循环可能被恶意输入触发无限修正 | 🔴高 | 反思循环总耗时限制60秒，总修正次数限制3次，超限强制返回 |
| S-2 | 策略脑的意图理解基于关键词匹配，可能被prompt注入误导 | 🟡中 | StrategistBrain.understand_intent()需对user_input做sanitize（复用InputValidator），不直接拼接 |
| S-3 | PHASE4技能市场API需认证和权限控制 | 🟡中 | G6必须包含API Key认证+技能权限分级（读/写/执行），不可裸API |
| S-4 | 插件系统沙箱隔离是安全红线 | 🔴高 | G8的插件必须运行在受限环境中，禁止访问文件系统/网络/环境变量，除非显式授权 |

### 🧪 测试专家审核

**认可点**:
1. 现有408个测试提供了良好的回归基线

**风险与改进**:

| # | 风险 | 严重度 | 改进建议 |

| T-1 | AgentLoop+TaskEngineV3集成缺少端到端测试 | 🔴高 | 新增集成测试：用户输入→AgentLoop→策略脑→执行脑(TaskEngineV3)→反思脑→输出，覆盖5种IntentType |

| T-4 | PHASE4 API测试需包含安全测试 | 🟡中 | G6测试计划需包含：未认证访问、越权调用、注入攻击 |

- G1-G5: 新增≥30个集成测试

- 全量回归: 408+测试100%通过

### 💻 开发者审核

**结论**: ✅ 通过

**认可点**:
1. 方案的技术路径清晰，不需要重写TaskEngineV3
2. TaskEngineAdapter的适配器模式是标准做法，风险可控

**风险与改进**:

| # | 风险 | 严重度 | 改进建议 |
|---|------|--------|---------|
| D-1 | ExecutorBrain当前_execute_skill_mock()需要替换为真实调用 | 🔴高 | TaskEngineAdapter封装：skill_id→TaskEngineV3._execute_*()方法映射，mock仅作为降级 |
| D-2 | StrategistBrain的意图分类和IntentClassifier的分类体系不同（6种IntentType vs 5种TaskType） | 🔴高 | 需要映射表：IntentType→TaskType，确保策略脑的每个意图都能路由到TaskEngineV3的对应方法 |
| D-3 | AgentLoop.run()返回Dict，TaskEngineV3.execute()返回TaskResult | 🟡中 | 需要结果转换层：AgentLoop的Dict→TaskResult格式，保持前端兼容 |
| D-4 | EventEmitter的队列在Streamlit中如何消费？ | 🟡中 | Streamlit不支持AsyncIterator，需用st.session_state轮询或st.empty()占位刷新 |

**实现建议**:
- 新增`opc_manager/task_engine_adapter.py`（~150行），封装skill_id→TaskEngineV3映射
- 修改`frontend/app.py`：新增`execute_with_agent_loop()`函数，与现有`execute_task_and_deliver()`并存
- 新增环境变量`OPC_USE_AGENT_LOOP=true/false`控制入口选择
