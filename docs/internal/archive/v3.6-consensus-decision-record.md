### 2.2 🏗 架构师 (ARCH) 发现

#### 架构健康度审计

```
✅ 做得好的地方:
  1. 模块边界清晰: 4个P0组件职责单一，接口明确
  2. 降级设计完善: 每层都有fallback，不会级联崩溃
  3. 测试覆盖充分: 143个测试，核心路径全覆盖
  
⚠ 需要关注的技术债:
  T-ARCH-1: SearchResultProcessor的正则分词过于简单
    → 中文"Q2营销方案"依赖滑动窗口切分，准确率约70%
    → 风险: 复杂查询可能切分错误导致关键词丢失
    → 建议: v3.6引入jieba轻量版(可选依赖)，正则作为降级
    
  T-ARCH-2: AsyncTaskExecutor的内存队列不可扩展
    → 当前: dict存储任务状态，进程重启即丢失
    → 风险: 生产环境无法多实例部署
    → 建议: v3.6引入Redis作为可选backend（有Redis用Redis，无则保持内存）
    
  T-ARCH-3: SessionContextManager无持久化
    → 刷新页面=丢失所有对话历史
    → 风险: 用户体验断裂
    → 建议: v3.6增加SQLite本地存储选项
    
  T-ARCH-4: LLMEnhancedContentGenerator的RAG模式复杂度高
    → _build_prompt()方法~80行，逻辑分支多
    → 风险: 维护成本高，新开发者理解门槛大
    → 建议: 提取PromptTemplate类，将prompt构建策略化
    
  T-ARCH-5: SearchCache的50条上限可能不够
    → 高频场景下命中率下降快
    → 风险: 重复搜索浪费API调用
    → 建议: 动态调整上限(根据内存占用自适应)
```

#### 技术优化提案（ADR风格）

| ADR# | 标题 | 问题 | 方案 | 权衡 | 投票 |
|-------|------|------|------|------|------|
| **ADR-011** | **NLP分词引擎选型** | 正则分词准确率70% | 引入jieba(可选依赖)，正则降级 | +30%准确率 vs +5MB包体积 | 🟢v3.6 |
| **ADR-012** | **任务队列Backend抽象** | 内存队列无法多实例 | 定义QueueBackend接口，Memory/Redis双实现 | +扩展性 vs +复杂度 | 🟢v3.6 |
| **ADR-013** | **会话持久化方案** | 刷新丢历史 | SQLite本地存储 + session_id cookie | +用户体验 vs +IO开销 | 🟡v3.6.1 |
| **ADR-014** | **Prompt模板化** | RAG prompt构建复杂 | PromptTemplate类 + 策略模式 | +可维护性 vs +抽象层次 | 🟡v3.7 |
| **ADR-015** | **SearchCache自适应** | 固定50条不够 | LRU-K算法 + 内存监控动态调整 | +命中率 vs +CPU开销 | 🔴v3.7 |

#### ARCH顾虑
```
⚠ 过度架构风险:
  - Redis/消息队列: 对于当前规模(<100并发)完全不需要
    → YAGNI原则: 在真正遇到瓶颈前不要优化
    → 建议: ADR-012只做接口定义，不实现Redis backend
    
⚠ jieba依赖风险:
  - 引入NLP库会增加部署复杂度(需要编译)
  - 中文分词对搜索质量的实际提升待验证
    → 建议: 先用真实数据集评测正则vsjieba的效果差异，再决定是否引入
```

```
📊 当前测试统计:
```

```
  - 但移动端查看结果的需求存在

```

### 3.2 冲突点与解决

#### 冲突1: NLP分词引擎(jieba) — ARCH提出 vs PM/QA质疑

```
ARCH观点: 正则分词准确率70%，应引入jieba提升到90%+
PM质疑:  增加部署复杂度(+5MB)，用户是否感知到差异？
QA补充: 需要用真实数据集A/B测试才能证明有效

→ 共识决策:
  ✅ ADR-011采纳(jieba作为可选依赖)
  ✅ 但不做默认启用(需配置ENABLE_JIEBA=true)
  ✅ v3.6先做效果对比实验，v3.6.1再决定是否默认开启
```

#### 冲突2: Redis任务队列 — ARCH提出 vs PM反对

```
ARCH观点: 内存队列无法多实例，生产环境需Redis
PM反对: 当前<100用户，YAGNI原则，过早优化
UI补充: 前端只需polling接口，不在乎backend实现

→ 共识决策:
  ✅ ADR-012采纳(定义QueueBackend接口)
  ✅ 仅实现MemoryBackend(现有逻辑封装)
  ✅ RedisBackend留作v3.7选项(当并发>50时再考虑)
```

#### 冲突3: E2E测试工具选择 — QA想用Playwright vs UI担心可行性

```
QA观点: pytest-playwright可以测试Streamlit(通过chromedriver)
UI担忧: Streamlit是SPA，DOM动态生成，选择器不稳定
ARCH补充: 可以用st.testing TestingHooks替代(官方推荐)

→ 共识决策:
  ✅ 采用分层策略:
    - L1: st.testing hooks(单元级组件测试) → 立即
    - L2: playwright(关键路径冒烟) → v3.6.1
    - L3: 手动探索性测试(每周1次) → 持续
```
